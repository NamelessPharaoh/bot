# CEO Plan: MCP Control Surface for the WOS Bot
Generated by /plan-ceo-review on 2026-09-07
Branch: main | Mode: SELECTIVE EXPANSION
Repo: NamelessPharaoh/bot

## Problem

The user wants to drive the WOS Discord bot from Claude: issue operational
commands and have it post guides. They already have three ways to *write* to the
bot (Discord admin menus reachable from a phone, SSH, and a `git push` that
auto-deploys within 5 minutes via `wos-deploy.timer`). What they have no way to
do is let Claude **read** the bot's state without the user hand-relaying logs and
status into a chat window.

Chosen surface: Claude Desktop. Chosen authority: read, post, and a fixed,
enumerated set of safe ops. No deploys, no permission changes, no gift-code
redemption runs, and no arbitrary database writes.

Five tools change state. They are named here exhaustively and nothing else may
mutate anything:

| Tool | Phase | What it changes |
| --- | --- | --- |
| `post_guide` | 1 | a Discord channel |
| `clear_queue` | 2 | rows in `settings.sqlite` |
| `create_backup` | 2 | files in `backups/` |
| `reload_cog` | 2 | the live extension registry |

Every call also appends to `log/mcp.txt`. Phase 1's only state change outside
this host is a webhook post to one Discord channel; it mutates nothing in the
bot. `restart_bot` appeared in earlier drafts and was dropped entirely (see
"Dropped entirely: restart_bot").

## Vision

### 10x Check

Claude stops waiting to be asked. A scheduled `claude -p` run reads bot state
through the same MCP tools every N minutes and messages the user only when
something is actually wrong: queue stalled, a cog failed to load, a deploy rolled
back, redemption failures spiking. The read plane makes this nearly free once it
exists. Deferred to TODOS (E2) because thresholds tuned against unproven tools
produce alerts that get muted.

### Landscape finding (Layer 3 eureka)

The conventional framing, "build an MCP server for my Discord bot", bundles two
things with opposite risk profiles:

- **Posting to Discord is a commodity.** Seven-plus open-source Discord MCP
  servers already exist, some with 46 to 134 tools, all working with Claude
  Desktop.
- **Reading the bot's internal state is the only differentiated half.** Cogs
  loaded, queue depth, OCR sessions, FD count, redemption records. No
  off-the-shelf server can reach any of it.

The correct conclusion is narrower than the first draft of this plan claimed. See
"Security properties" below for what the split does and does not buy.

## Transport constraint (verified, not assumed)

- The host has no web server, no TLS, no domain. Only `:22` is open publicly.
- **Claude Desktop** runs a local stdio MCP server, which can be an SSH wrapper
  into this box. No new port is opened. Works today.
- **claude.ai / mobile** needs a remote connector: OAuth 2.1, PKCE, HTTPS, and a
  publicly exposed endpoint. That is a separate build and puts an authenticated
  control endpoint for the bot on the public internet.

Decision: build for Claude Desktop over SSH now. Treat claude.ai exposure as a
separate, later decision.

## Chosen approach: B, split-plane

Rejected alternatives:

- **A: read-only, zero bot changes.** Completeness 6/10. Safest, but drops guide
  posting and cog reload, roughly half the ask.
- **C: single server + full control cog** (the first sketch). Completeness 10/10
  but rebuilds what `systemctl` and `sqlite3` already do.

B's shape:

1. One custom **stdlib-only** MCP server (`tools/wos_mcp.py`), run over SSH from
   Claude Desktop. MCP is JSON-RPC over stdio, so no SDK and nothing added to
   `requirements.txt`.
2. **Guide posting via a Discord webhook only.** No bot token is ever handed to a
   posting path, and no third-party MCP package is installed.
3. A **single-purpose cog** for the three operations that genuinely cannot work
   from outside the process.

### Decision: the webhook is the only posting path

The first draft had both a webhook and a post-as-the-bot cog path with no
criterion for choosing. Resolved: **webhook only.** Guides are long-form prose
that does not need the bot's identity, and a webhook is clearly attributed to a
separate identity, which is a feature. Consequences:

- The cog never touches Discord messaging, which removes an entire class of rate
  limit, permission, and gateway failure from it.
- If theme-native embeds later prove necessary, that is a new decision, not an
  unstated fallback.

## Tool table (authoritative; supersedes every earlier count in this document)

Final after the CEO review, the eng review, and two outside-voice passes.
**Ten tools. Phase 1 is six. Phase 2 is four.**

| # | Tool | Kind | Phase | Why |
| --- | --- | --- | --- | --- |
| 1 | `bot_status` | read | 1 | `db/`, `/proc/<pid>/limits`, `/proc/<pid>/fd`, `systemctl is-active` |
| 2 | `queue_status` | read | 1 | `process_queue` rows in `settings.sqlite` |
| 3 | `read_log` | read | 1 | allowlisted basenames under `log/`, plus `.txt.1` |
| 4 | `query_db` | read | 1 | SQLite, three-layer read-only enforcement |
| 5 | `explain_error` | read | 1 | streams `log/*.txt`, bounded buffers |
| 6 | `post_guide` | post | 1 | Discord webhook |
| 7 | `reload_cog` | op | 2 | live extension registry; hand-curated safe list |
| 8 | `live_state` | read | 2 | extension registry, `_current_process`, OCR refcounts |
| 9 | `create_backup` | op | 2 | 107-line pipeline, all-relative paths, encryption |
| 10 | `clear_queue` | op | 2 | must coordinate with the worker's claim protocol |

**Phase 1 mutates nothing in the bot.** Its only outward effect is a webhook post.
This is a deliberate reversal: earlier drafts placed `restart_bot`, `clear_queue`
and `create_backup` in Phase 1, and all three moved or were dropped once their
correctness was actually checked.

### Dropped entirely: `restart_bot`

Removed by decision Y3. Three reasons, in order of weight:

1. Its interlock does not work. Holding `/var/lib/wos-deploy/lock` serializes
   against deploys only; queue producers never take that lock, so work can still
   start between the busy check and the restart. The TOCTOU the eng review
   claimed to close was never closed.
2. Two existing surfaces already do it: `systemctl restart wos-bot` over SSH, and
   the Bot Health button reachable from a phone.
3. It was the only Phase 1 tool that could take the bot offline. Removing it makes
   the Phase 1 blast radius "read anything, post to one channel."

## Phasing, and the gate that has to be real

- **Phase 1** ships tools 1 through 6: every read tool plus webhook posting. It adds **zero** bot code, so `main.py`'s cog list is untouched
  and `wos-deploy`'s untested rollback path is never approached. It is still not
  free of consequence: the Phase 1 commit itself triggers an unattended deploy
  and a live `systemctl restart` of the bot within 5 minutes of landing on
  `main`.
- **Phase 2** adds `cogs/mcp_control.py` with `reload_cog`, `live_state`,
  `create_backup`, and `clear_queue`.

### Phase 2 needs a transport, and the second draft had none

The outside voice caught this and it is a straight error, not a tension: the MCP
server is a separate SSH process and the cog lives inside the bot process, and no
draft of this plan connected them. "Needs the cog" is not an architecture. The
socket was dropped when the plan moved from approach C to approach B and was
never replaced.

Required for Phase 2: a Unix domain socket at the install root, mode `0600`,
owned by the bot's user. Newline-delimited JSON, one request per connection, with
a version field following `roster_intake`'s versioned-protocol precedent. The cog
owns the listener's lifecycle in `cog_load` / `cog_unload` and unlinks a stale
socket file on startup. The server side uses a 5-second connect-and-read timeout
and degrades to `error: "bot_unreachable"` rather than blocking, so a wedged bot
never wedges the MCP session. No authentication beyond filesystem permissions,
which is the same trust model as the forced command.

### The Phase 2 dependency

`TODOS.md` item 1 records that `wos-deploy`'s rollback path has never executed,
and names the exact trigger: *"a cog that raises on load."* Phase 2 adds a cog to
`main.py`'s `load_cogs()`, and `wos-deploy.timer` fires unattended every 5
minutes. **Phase 2 is the first real customer of TODOS item 1.**

Corrected from the first draft: the readiness check is **not** a hazard.
`wait_ready()` in `/usr/local/sbin/wos-deploy` greps the generic
`[0-9]+/[0-9]+ modules loaded` and compares `loaded` to `total`, so the count
moving from 31/31 to 32/32 passes normally. Verified by reading the script.

The real hazard is that **there is currently no gate at all.** A Phase 2 commit
to `main` deploys itself within 5 minutes with nobody watching. Required before
Phase 2 lands:

1. Develop Phase 2 on a branch. `wos-deploy` skips any HEAD that is not `main`
   (verified: it exits 0 with "on '<ref>', not 'main'; skipping"), so a branch is
   a real gate, not a convention.
2. Exercise TODOS item 1 deliberately first, on a quiet evening, with a
   throw-away cog that raises on load. Pass condition: the bot returns to the
   previous commit, restarts, reports `N/N modules loaded`, the script exits
   non-zero, and the SHA is recorded in `/var/lib/wos-deploy/last-failed` and
   skipped on the next tick.
3. Only then merge Phase 2 to `main`.

Owner: the user. This plan does not authorize step 2 to happen automatically.

## Security properties: what this design does and does not buy

The first draft claimed "the thing that can post to the alliance never has the
power to restart the bot." **That claim is false as designed** and is withdrawn.
`post_guide` and `restart_bot` are tools on the same server, reached over the
same SSH session by the same agent.

What the split actually buys, stated accurately:

- **No Discord bot token is ever handed to a posting path.** The webhook URL is a
  strictly weaker credential: it can post to exactly one channel and can do
  nothing else. On leak, the blast radius is one channel, not the bot.
- **No unaudited third-party package holds a credential.** Given `7343295`, where
  a live token nearly reached a public repo, this is not hypothetical.

### Prompt injection (unaddressed in the first draft)

`read_log`, `query_db`, and `explain_error` all ingest attacker-influenceable
text into the same context that holds `restart_bot`, `clear_queue`, and
`post_guide`. Log lines carry Discord-sourced content; `users.nickname` and
OCR'd player names are written by alliance members. Required:

- All tool output is returned fenced and explicitly labelled as untrusted data,
  never as instructions.
- Every mutating tool (`post_guide`, `clear_queue`, `create_backup`,
  `reload_cog`) requires an explicit `confirm` argument.
  **Correction to the second draft:** this is not an injection control. The model
  composes the tool call, so it supplies `confirm` as readily as any other
  argument. What it actually buys is protection against *accidental* invocation
  and a clear audit signal. The real gate against an injected instruction is
  out of band: Claude Desktop's own per-call approval prompt, which the user must
  leave enabled for the four mutating tools. That is named here as the control
  rather than implied.
- The webhook is created with `allowed_mentions: {"parse": []}` so a guide can
  never `@everyone`, no matter what text reaches it.

### SSH authority (unaddressed in the first draft)

`systemctl restart wos-bot`, `/proc/<pid>/fd`, and `Bot-runtime/db/*` all require
root: the unit runs `User=root` with `WorkingDirectory=/root/bot/Bot-runtime`.
"No new port is exposed" is true of ports and misleading about authority. This
design hands the MCP client root authority over `:22`.

**The sudoers split proposed in the second draft is infeasible and is withdrawn.**
Verified on this host:

- `/root` is `drwx------ root root`. An unprivileged user cannot **traverse** into
  it, so `Bot-runtime/db/` and `log/` are unreachable regardless of their own
  modes.
- `/proc/<pid>/fd` is `dr-x------ root root`, so E1's FD **count** needs root or
  `CAP_SYS_PTRACE`. (`/proc/<pid>/limits` is `-r--r--r--`, so the ceiling is
  readable unprivileged; the count is not.)
- Sudoers grants command execution, not file-read permission. "Read access to
  `db/` and `log/`" is not an expressible sudoers rule, and papering over it with
  `sudo cat` or `sudo sqlite3` wrappers is strictly worse than root: `sqlite3`'s
  `.shell` is a root shell and `sudo cat <path>` is arbitrary root file read.
- The `ghrunner`/`ace-deploy` analogy does not transfer. `ghrunner` only needs to
  *invoke* one script; this needs to *read* files under `/root`.

Under the split, five of the six Phase 1 tools fail (only `post_guide` survives). Decision, stated honestly:

**The entry script runs as root, and the forced command is the entire security
boundary.** Its argument validation is therefore load-bearing, not defence in
depth. Required:

- A dedicated ed25519 key used for nothing else.
- `command="/usr/local/sbin/wos-mcp-entry",restrict` in `authorized_keys`. The
  client cannot choose what runs, cannot request a PTY, port forwarding, agent
  forwarding, or X11.
- The entry script accepts **no arguments from the client at all**. It execs the
  server with a hard-coded install root (this is the "mandatory argument with no
  default" from Correctness requirements, supplied by the entry script rather
  than by the client). Everything the client can influence
  arrives as JSON-RPC on stdin and is validated by the tool layer.
- Every tool invocation is appended with its arguments to `log/mcp.txt`.

The rejected alternative, recorded so it is not rediscovered: POSIX ACLs
(`setfacl -m u:wos-mcp:x /root` plus `-R -m u:wos-mcp:rX` on `db/` and `log/`)
with a setuid helper or `AmbientCapabilities` for `/proc/<pid>/fd`. That works,
but it punches a permanent hole in `/root`'s `0700` for a second principal, which
is a worse trade than a forced command.

**The trade stated on the axis that actually decides it**, because the framing
above omits it: under forced-command-as-root, **a stolen client key is root on
this box**. Under ACLs, a stolen key reads `db/` and `log/` and can post to one
channel. This plan chooses the larger blast radius on key compromise in exchange
for not weakening `/root`. That is a real trade and the user should make it
knowingly. Key handling is therefore load-bearing: the client-side private key
must be passphrase-protected, and an `authorized_keys` `from=` clause restricting
the source address should be added if the user's IP is stable.

## Correctness requirements

### query_db must block ATTACH (verified hole)

The first draft asserted that a `?mode=ro` URI makes the driver enforce
read-only. **That is wrong, and was verified wrong on this host** (Python 3.14,
SQLite 3.46.1): `mode=ro` blocks a direct `INSERT`, but

```
ATTACH 'file:/tmp/other.db?mode=rwc' AS x;  INSERT INTO x.z VALUES(9);
```

succeeds and writes another file. `PRAGMA query_only=ON` is not the fix either,
because submitted SQL can turn it back off. Required, all three:

1. Open with `file:<path>?mode=ro` and `uri=True`.
2. `conn.setlimit(sqlite3.SQLITE_LIMIT_ATTACHED, 0)` (verified to raise
   `too many attached databases - max 0`).
3. A `set_authorizer` callback denying `SQLITE_ATTACH` and every write opcode.

The first draft's supporting claim about "CTE-wrapped writes" was also wrong for
SQLite and is removed: `WITH ... INSERT` does not begin with `SELECT`, and SQLite
has no writable CTE inside a `SELECT`. The conclusion stands; the reasoning was
faulty and would have misled an implementer into shipping the hole.

### Client-supplied identifiers must be allowlisted, not merely validated

This applies to **every** value the client controls: file paths, database names,
and module names alike. The narrow "paths" framing of the previous draft let a
module name slip past it. See the `reload_cog` hazard below.

The server runs as root (see above), so an unconstrained path argument is an
arbitrary root file read reachable by the exact injected-model path the security
section acknowledges. `read_log("../bot_token.txt")` and a `query_db` pointed at
`WOS-manager/.../ace.sqlite` (which `CLAUDE.md` records as sitting beside
artifacts carrying a live `DISCORD_TOKEN` and `ACE_BACKUP_KEY`) are both reads
the ATTACH defence does nothing about: that defence guards writes and says
nothing about which file gets opened. Required:

- `read_log` accepts only a basename from a fixed set: `bot`, `alliance`, `gift`,
  `redemption`, `notification`, `rapidocr`, `backuplog`, `mcp` (all `.txt`).
- `query_db` accepts only the known database filenames under the install root's
  `db/`.
- Both resolve with `Path.resolve()` and reject any result that escapes the
  install root, as a second layer behind the allowlist.
- `read_log` must also allow the single rotation `<name>.txt.1`. `main.py` uses
  `RotatingFileHandler(maxBytes=2MB, backupCount=1)`, so a 2MB burst pushes the
  interesting traceback into the older half, which is exactly when it is wanted.
  `log/archive/` stays out of scope; `explain_error`'s glob is non-recursive and
  takes no client-supplied path at all.
- The `query_db` allowlist is a **literal tuple in the source**, not "the known
  filenames", so it is reviewable. It **excludes `backup.sqlite`**: that file's
  `backup_passwords` table stores passwords in a form `_write_db_zip` hands
  straight to pyzipper, so reading it yields the key to every encrypted archive
  in `backups/`. The `create_backup` requirement to resolve a real password and
  the `query_db` allowlist interact badly, and this is the resolution.

### reload_cog's argument is the same hazard, and needs the same treatment

`cogs/` holds **55** `.py` files; `main.py`'s `load_cogs()` loads **31**.
`bot_health.reload_cogs()` (`cogs/bot_health.py:1364-1372`) falls through to
`load_extension(ext_name)` for anything not already in `bot.extensions`. Since
Phase 2 reuses `bot_health` for E4's real busy summary, the natural
implementation of `reload_cog` inherits that fallback, and
`reload_cog("<any of the 24 unloaded modules>")` loads never-vetted code into the
live root process. Required:

- **Superseded requirement, kept only as a warning.** An earlier draft required
  "names present in `main.py`'s `load_cogs()` list and currently in
  `bot.extensions`." That rule is UNSAFE and must not be implemented: it permits
  `reload_cog("process_queue")`, which is a verified P0 (see decision Y1). Do not
  derive the allowlist from the load list.
- **Required:** a short, hand-curated list of genuinely stateless cogs, each with
  a written reason it is safe to hot reload. Refuse everything else, including
  `process_queue`, `onnx_lifecycle`, `notification_schedule`, `bot_backup`,
  `bot_health` (which already refuses itself at `cogs/bot_health.py:1358`), and
  `mcp_control`.
- Never use the load-if-absent path.

### query_db must bound cost, not just output

The 500-row and 256KB caps bound the response. They do not bound a cartesian join
that burns CPU for minutes before producing its first row, on the same box as the
live bot. Required: `conn.set_progress_handler(deadline_check, 10000)` with a
wall-clock budget of 3 seconds that raises, alongside the row and byte caps.

### Install root must be explicit

`/root/bot` (the repo) has **no `log/` directory** and carries a stale `db/` with
6 SQLite files. A server started from the repo tree would answer `bot_status` and
`queue_status` with dead data and no error at all. Required: the install root is
a mandatory argument or environment variable with **no default**, and the server
exits non-zero at startup if `log/` is absent under it. The only valid value
today is `/root/bot/Bot-runtime`.

### Failure handling

Every tool returns one error envelope: `{"ok": false, "error": <code>,
"detail": <string>}`. Explicitly specified cases:

- Bot down: `db/` readable but `/proc/<pid>` gone. `bot_status` reports
  `running: false` rather than erroring.
- `database is locked`: the server sets a 5s busy timeout and returns
  `error: "db_locked"` rather than hanging. The bot's own connections use
  `timeout=30.0`, so the server must never be the one that waits longest.
- `query_db`: hard cap of 500 rows and 256KB of response, whichever comes first,
  reported as truncated. MCP responses land in the context window.
- `read_log`: tail-only, capped at 64KB, never the whole 2MB file.
- Webhook 429: surface the `retry_after` value, never auto-retry in a loop.
- `reload_cog` raising: return the exception text; do not attempt a restart.

### MCP protocol conformance

"Stdlib-only" is achievable but was understated. A conformant server needs
`initialize` with protocol-version negotiation, `notifications/initialized`
(which must produce no response), `tools/list` with a JSON Schema per tool,
`tools/call` returning content blocks, `ping`, and correct error objects.
Required: pin the protocol revision explicitly in the source, and add a test that
drives stdin/stdout through a scripted `initialize` to `tools/list` to
`tools/call` handshake. Deferring E5 for having "no test to catch a drift" while
shipping an unpinned protocol implementation would be the same mistake.

### Packaging

`tests/` is kept out of the release payload by `tests/ export-ignore` in
`.gitattributes`. `tools/` has no such line. Required: add `tools/ export-ignore`
in the same commit, or the MCP server ships to every user of the bot.

### The create_backup trap (verified)

`BotBackup.create_backup(user_id, ...)` looks up
`SELECT backup_password FROM backup_passwords WHERE discord_id = ?`
(`cogs/bot_backup.py:322`). **A reserved non-Discord sentinel id has no row**, so
`backup_password` is `None` and `_write_db_zip` writes a **plain, unencrypted
zip** while every user-triggered backup is AES encrypted via pyzipper.

That means the one backup path an injected agent could trigger unattended is
precisely the path that drops encryption, dumping every table (admin ids, member
rosters, redemption records) as plaintext into `backups/`. Given `7343295`, where
a rollback artifact carrying a live token was swept into a commit against a
public repo, plaintext database dumps accumulating next to that repo are the same
shape of accident. Required:

- The MCP path must resolve a **real** password, either by reusing the bot
  owner's `backup_passwords` row or by provisioning a dedicated row at install,
  and must **refuse to run** if none exists. Never fall through to `None`.
- Call `can_create_backup(save_locally=True)` first. Both real callers do
  (`cogs/bot_backup.py:186` and `:565`); skipping it lets an MCP-triggered backup
  fill the disk.
- Distinguishability does **not** come from `backup.sqlite`, which holds only
  `backup_passwords` and `backup_settings` and has no backup-record table at all.
  It comes from the `backup_type` filename prefix plus an explicit `log_backup()`
  call, which the caller must make.

### HISTORICAL: restart_bot is not the same operation as the Bot Health button

**`restart_bot` was dropped by decision Y3. This section is retained only to
record why its interlock could not be made correct, which is one of the three
reasons it was cut. Do not implement anything in it.**

Worth stating because E4 compares them on carefulness. `systemctl restart
wos-bot` sends `KillSignal=SIGINT` and re-executes `main.py --no-update` as a
fresh process; the Bot Health button calls `os.execl` and keeps the PID
(`cogs/bot_restart.py`). They are different operations with the same name.

The proposed fix (refuse while `wos-deploy` holds its `flock` on
`/var/lib/wos-deploy/lock`) was later shown to be insufficient: that lock
serializes against deploys only, and queue producers never take it, so work can
still begin between the busy check and the restart. That unclosable race is
reason 1 in "Dropped entirely" above.

## Scope Decisions

| # | Proposal | Effort | Decision | Reasoning |
|---|----------|--------|----------|-----------|
| E1 | FD-count tripwire in `bot_status` | S (CC ~15 min) | ACCEPTED | Targets the bug class that recurred three times (`89e4c43`, `673df93`, `553d077`). |
| E2 | Proactive alerting cron | M (CC ~30-45 min) | DEFERRED | Highest value in the scan, but depends on a read plane proven in production. |
| E3 | `explain_error` log triage tool | S (CC ~30 min) | ACCEPTED | Groups and counts distinct tracebacks instead of dumping tails. |
| E4 | Reuse `bot_health`'s busy interlock in the ops tools | S (CC ~20 min) | ACCEPTED, with a stated Phase 1 limit | See below. |
| E5 | Deploy-history tool reading `wos-deploy` state | S (CC ~15 min) | DEFERRED | `wos-deploy` is untracked; `journalctl` already answers this. |
| E6 | Point the same server at `ace-bot` | S-M (CC ~20 min) | DEFERRED | Premature abstraction before the first target has run once. |

### E1 correction

The first draft had E1 read `LimitNOFILE=65536` from
`/etc/systemd/system/wos-bot.service.d/limits.conf`, an untracked root-owned
path. That is the same coupling used to justify deferring E5, applied
inconsistently. Corrected: read `/proc/<pid>/limits` instead. Same number, no
untracked path, no drift.

### E4's Phase 1 limit, stated plainly

`bot_health._active_work_summary()` needs the live bot object: it calls
`ProcessQueue.get_queue_info()`, whose `is_processing` is the in-memory
`self._current_process is not None`, and reads `onnx_lifecycle._REGISTRY`
refcounts. **None of that is visible from outside the process.** Therefore:

- **Phase 1's interlock is a database-only approximation**: it counts
  `process_queue` rows with `status IN ('queued','active')`. **OCR sessions in
  flight are invisible to it.** This was the argument for a Phase 1
  `restart_bot` being *less* careful than the Bot Health button. With
  `restart_bot` dropped (Y3), E4 applies only to the Phase 2 mutating tools.
- **Phase 2 exposes the real summary through the cog**, at which point the MCP
  path and the button enforce the same gate.

The first draft claimed parity with the button in Phase 1. That was not
achievable and is corrected here.

## Accepted Scope

- `tools/wos_mcp.py`: stdlib-only MCP server over stdio, invoked via SSH, with a
  pinned protocol revision and a handshake conformance test.
- Phase 1 tools: `bot_status` (with the E1 `/proc/<pid>/limits` tripwire),
  `queue_status`, `read_log`, `query_db` (three-layer read-only enforcement),
  `explain_error` (E3), `post_guide` (webhook). **No `restart_bot`** and no
  other mutating tool: Phase 1 changes nothing in the bot.
- Phase 2: `cogs/mcp_control.py` carrying `reload_cog`, `clear_queue`, and
  `create_backup`, plus the real busy summary. Registered in `main.py`'s
  `load_cogs()`.
- `create_backup`: the second draft's spec was wrong on three checkable facts and
  is replaced. See "The create_backup trap" under Correctness requirements.
- SSH hardening: dedicated key, forced command running **as root**, entry script
  accepting no client arguments and ignoring `SSH_ORIGINAL_COMMAND`, scrubbed
  environment, hard-coded interpreter and install root, per-call audit log to
  `log/mcp.txt`.
- `tools/ export-ignore` in `.gitattributes`.
- **Extend `wos-deploy`'s gate-1 test list, in this order.** pytest exits 4 on a
  missing path, so editing the gate list *before* `tests/test_wos_mcp.py` is on
  `main` makes every deploy fail, writes the SHA to `last-failed`, and stops

## Corrections folded in from the outside voice

These contradicted nothing in the plan and are treated as verified corrections:

- **The restart interlock is racy (TOCTOU).** The queue can be idle at check time
  and busy by the time `systemctl restart` lands. Same for the deploy-lock check
  unless the MCP process *acquires and holds* the flock across the restart.
  Required: hold the flock. Also note `systemctl restart` proves only that a
  `Type=simple` process launched, not that Discord connected or that cogs loaded,
  This was a requirement on `restart_bot`, which has since been dropped (Y3);
  it is recorded because any future remote-restart tool inherits the problem.
- **The SSH config in this plan does not implement its own security design.** A
  root forced command requires authenticating as `root`, but the recorded example
  connects as `wos-mcp@host`. The client entry also needs `IdentityFile`,
  `IdentitiesOnly=yes`, and a pinned host key, and a passphrase-protected key
  launched non-interactively needs an explicit agent or keychain arrangement.
  The recorded config below is corrected accordingly.
- **`query_db` resource limits go beyond the progress handler.** A wall-clock
  budget bounds VM steps, not single-op allocations (`randomblob()`), oversized
  values fetched before truncation, or temp storage. Required: set
  `SQLITE_LIMIT_LENGTH`, `SQLITE_LIMIT_SQL_LENGTH`, `SQLITE_LIMIT_COLUMN`, and
  `SQLITE_LIMIT_EXPR_DEPTH`; constrain temp storage; and cap the incoming
  JSON-RPC line length *before* parsing it.
- **`create_backup` retention and collisions.** `can_create_backup()` only checks
  space for the next backup. MCP-triggered backups need a retention limit, a
  cooldown, and mutual exclusion with the automatic backup loop. Filenames are
  second-resolution (`cogs/bot_backup.py:328`) and can collide and overwrite.
- **`post_guide` needs a delivery design, not just a chunker.** Define message
  ordering, idempotency, partial-failure behaviour, and specifically what happens
  when message three of five gets a 429. `allowed_mentions` solves one small
  failure mode and no others.
- **The audit log is not an audit log as specified.** Every caller shares one SSH
  identity, arguments are attacker-influenced, and `read_log` can read `mcp.txt`
  itself, which makes it persistent injection content that can also be forged
  with newlines. Required: structured records with escaping, locking, rotation,
  size limits, redaction, and a connection fingerprint. Otherwise stop calling it
  an audit trail and call it a debug log.

## Engineering review decisions (2026-09-07)

Seven issues, all settled. Two of them reverse conclusions the CEO review had
accepted from the outside voice.

**Issue 1, socket acquisition: probe-then-unlink.** Verified that all three
restart paths orphan the socket file, so the plan's "unlink a stale socket on
startup" is the primary path, not a corner case:

- `cogs/bot_health.py:1458` calls `restart_process()` with no `bot.close()`
  anywhere before it, and `cogs/bot_restart.py` uses `os.execl`, replacing the
  image so `cog_unload` never runs.
- A crash under `Restart=always` never runs it either.
- On SIGINT, discord.py 2.7.1's `Bot.close()` unloads extensions in insertion
  order. `process_queue` is 2nd of 31 and its `cog_unload` does
  `await asyncio.wait_for(self._processor_task, timeout=30.0)`
  (`cogs/process_queue.py:78`), which is exactly `TimeoutStopSec=30s`. A cog
  appended 32nd is SIGKILLed before its cleanup runs.

Required: try to connect to an existing socket first. Connect succeeds means a
live instance owns it, so refuse. `ECONNREFUSED` means it is stale, so unlink and
bind. Give the probe a short connect timeout so a wedged predecessor cannot stall
startup.

**Issue 2, load-failure posture: degrade loudly, never raise.** `main.py`'s
`load_cogs()` computes `loaded = total - len(failed_cogs)` and prints
`{loaded}/{total} modules loaded`; `wos-deploy`'s `wait_ready()` compares the two
numbers. So a `cog_load` that raises on a socket problem produces `31/32` and
fires the **never-exercised rollback path**, unattended, on a 5-minute timer.
Required: `cog_load` catches socket errors, logs at ERROR to `log/bot.txt`, and
sets a degraded flag. `reload_cog`, `live_state`, and `create_backup` then return
`error: "socket_unavailable"` with the original errno, and `bot_status` reports
the socket as down. A monitoring tool must never be the reason a deploy rolls
back.

**Issue 3, `create_backup` returns to Phase 2.** This reverses the CEO review's
acceptance of the outside voice on this point. Codex was right that SQLite's
online backup call is safe across processes, but that call is 12 lines inside a
107-line method, and every path in `cogs/bot_backup.py` is relative
(`self.db_path = "db/backup.sqlite"` at :25, `self.backup_dir = "backups"` at
:26, `os.listdir("db")` at :111 and :288). An external caller must therefore
either import the cog module, dragging `discord`, `pyzipper`, and `theme` into a
server whose whole justification is being stdlib-only, or reimplement 107 lines
of encryption-handling logic that already contains one verified silent-plaintext
bug. Neither is acceptable. It goes back behind the socket.

**Issue 4, `clear_queue` stays in Phase 1, with a corrected requirement.** The
plan required it to "clean orphaned `_runtime_contexts` entries." That is
impossible from another process: `_runtime_contexts` is a plain in-memory dict
(`cogs/process_queue.py:68`). It is also unnecessary, because
`attach_runtime_context`'s own docstring says entries are "Lost on restart by
design, handlers must fall back gracefully when missing." Corrected requirement:
the `DELETE` covers `queued` and `failed` rows only, and orphaned in-memory
contexts are left alone, which is the same state every restart already produces.

**Issue 5, socket testing: real sockets in `tmp_path`, no live bot.** The cog
must call a plain `bind_or_degrade(path)` helper that is testable without
discord.py. Binding and connecting a Unix socket in a pytest temp directory takes
milliseconds, so all three probe outcomes plus the bind failure are exercised
with real errnos rather than guessed ones. Mocking these was rejected: the test
guarding against a deploy rollback must not itself assert on a fiction.

**Issue 6, `restart_bot` polling budget (SUPERSEDED by Y3, which dropped the
tool; recorded for any future remote-restart tool).**
`wos-deploy` uses `READY_TIMEOUT=120`, but MCP clients enforce their own
per-request timeout, commonly around 60 seconds. Mirroring 120s would make a
successful restart report as a failure, and the natural retry would interrupt a
bot that is mid-boot. Poll for about 25 seconds, then return the readiness state
reached and direct the caller to `bot_status`.

**Issue 7, `explain_error` streams.** `log/` holds 1.5MB today but rotates at 2MB
with one backup across eight categories, so the ceiling is roughly 32MB
(`gift.txt` is already 1.09MB). Stream line by line with a bounded traceback
buffer so peak memory tracks the largest single traceback, not total log volume.

**Repo-ownership flag, not fixed:** `CLAUDE.md:54` states "Production runs Python
3.11" as a hard constraint, but `/root/bot/Bot-runtime/venv/bin/python3 -V`
reports **Python 3.14.4** and the venv path is `lib/python3.14/`. Keeping the
source 3.11-compatible remains correct for users who install on 3.11, and
`tests/test_python311_compat.py` still enforces it, but the stated justification
is stale and would mislead someone deciding whether the constraint still applies.

## Outside voice, second pass (eng review): corrections folded in

Codex returned "Reject as written" with 14 findings against the post-eng-review
document. Five were verified against the code and three forced reversals (Y1-Y3,
recorded below). These eight contradicted nothing and are folded in:

1. **Scope was unstable.** `clear_queue` had moved between phases three times and
   the tool counts contradicted each other in four places. Fixed: the tool table
   above is now the single authoritative source and says so.
2. **Probe-then-unlink is still racy** (Codex 2). Two initializers can both see a
   stale socket, one binds, the other unlinks the now-live socket and binds its
   own. A successful probe proves *a* listener exists, not that it is the right
   one. Required: hold an exclusive `flock` on a sidecar lock file across the
   whole probe-unlink-bind sequence, and define the connect-timeout branch
   explicitly (treat as LIVE, refuse).
3. **`socket_unavailable` cannot carry the cog's errno** (Codex 3). If the socket
   is unreachable the external server only knows its own connection error. The
   cog's stored errno is reachable only through `read_log` or `live_state`, both
   of which may be the thing that is broken. Required: the cog writes the bind
   failure to `log/bot.txt` at ERROR, and the server's error text says to look
   there rather than pretending to relay an errno it cannot see.
4. **The 5s socket timeout is shorter than the operations behind it** (Codex 4).
   `reload_cog` can spend 30s just unloading `process_queue`; backup compression
   is unbounded. A client that gets `bot_unreachable` while the mutation
   continues, then retries, recreates the duplicate-backup problem. Required:
   per-tool timeouts (5s for `live_state`, 60s for `reload_cog`, 300s for
   `create_backup`) plus an idempotency key on every mutating call.
5. **`create_backup`'s error contract needs `bot_backup.py` changed** (Codex 5,
   verified). The method has `except Exception: return None` at lines 413-416 and
   418-422, so it swallows everything. Retention, cooldown, collision prevention
   and exclusion against the automatic loop do not exist. Phase 2 must modify
   `bot_backup.py`; a new cog alone cannot deliver the promised contract.
6. **The busy gate is fail-open** (Codex 10, verified). `_active_work_summary()`
   (`cogs/bot_health.py:97`) has two `except Exception: pass` blocks and returns
   `None`, meaning idle, when both inspections fail. Required: distinguish idle
   from unknown, and treat unknown as busy for any mutating tool.
7. **The 32MB log ceiling was wrong** (Codex 11, verified, then corrected again).
   Six files rotate at 2MB with one backup (the five logging categories plus
   `rapidocr.txt`); `backuplog.txt` is a plain append with no ceiling at all, so
   the real shape is roughly 24MB bounded plus one unbounded file. Streaming is still right and now more so. Also cap the number of distinct
   traceback groups held in memory, not just the current buffer.
8. **Packaging and the test gate are still broken** (Codex 12, 13). `tools` must
   be added to `build_release.py`'s `EXCLUDE_DIRS`, not only to `.gitattributes`.
   And the gate-list edit sequencing does not work as written: after the test
   commit deploys, later timer ticks exit as already-deployed, so no candidate
   ever exercises the changed gate. The gate edit needs a deliberate no-op commit
   after it, or a manual `wos-deploy` run. Guarding the test on
   `tools/wos_mcp.py` existing also means deleting the server makes the suite
   pass silently; guard on the install root instead.
